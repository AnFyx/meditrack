# MediTrack

Jakarta EE application tracking patients and their attending doctors in a clinic, with asynchronous doctor assignment over a JMS queue.

Coursework for the Information Systems Analysis and Programming course at the University of Maribor (Erasmus+ exchange), written in June 2025. Reviewed and hardened in September 2026 before publication: see [History](#history-and-credits). Identifiers and the user interface are in English; comments are in French.

**This is a university exercise on EJB, JPA and JMS, not a production system. It has no authentication at all — see [Security](#security) before doing anything with it.**

## What it does

- Create, list, edit and delete patients and doctors, through a PrimeFaces web interface.
- Each doctor has a patient quota (`maxPatients`).
- A patient can request a doctor. The request goes into a JMS queue; the REST layer only acknowledges it (HTTP 202).
- A message-driven bean consumes the queue, checks the quota, records the assignment, and sends e-mail notifications to the patient and to the doctor, or a rejection if the doctor is full.
- A JAX-RS API exposes the same operations, used by a command-line client.

## Architecture

```
MediTrack_V7/                     WildFly web application (WAR)
└── src/main/java/aiv/
    ├── vao/                      JPA entities: Person (abstract), Doctor, Patient
    ├── ejb/                      Stateless session beans, one DAO per entity
    ├── rest/                     JAX-RS resources under /api
    ├── jsf/                      CDI beans backing the Faces views
    ├── jms/                      Message-driven bean and mail notifications
    └── dto/                      Serialisable payload carried by the queue
MediTrackClient/                  Command-line client (JAR) calling the REST API
```

`Person` is mapped with `InheritanceType.JOINED`, so `Doctor` and `Patient` share the `person` table and add their own. The queue payload carries only the two e-mail addresses, not whole entities, so the consumer always reloads fresh state from the database.

| Layer | Technology |
|---|---|
| Platform | Jakarta EE 10, Java 21 |
| Server | WildFly (deployed with `wildfly-maven-plugin`) |
| Persistence | JPA over MySQL, JTA datasource `java:/MySqlDS` |
| Messaging | JMS queue `java:/jms/queue/DoctorSelectionQueue` |
| Web | Jakarta Faces 4 with PrimeFaces 13 |
| Mail | Jakarta Mail through the `java:/mail/MyMail` server resource |

## Configuration

Nothing in this repository holds a credential. The datasource and the mail session are configured in WildFly, which keeps host names, users and passwords in the server configuration:

```bash
# MySQL datasource used by the persistence unit
jboss-cli.sh --connect
data-source add --name=MySqlDS --jndi-name=java:/MySqlDS \
  --driver-name=mysql --connection-url=jdbc:mysql://localhost:3306/mediTrack \
  --user-name=<db-user> --password=<db-password>

# JMS queue consumed by the message-driven bean
jms-queue add --queue-address=DoctorSelectionQueue --entries=[java:/jms/queue/DoctorSelectionQueue]
```

The mail session `java:/mail/MyMail` must point at an SMTP server with its own credentials. Store the SMTP password in the WildFly credential store rather than in `standalone.xml` in clear text. The repository's `.gitignore` excludes `standalone*.xml` and `*-ds.xml` so a local server configuration cannot be committed by accident.

The database schema is not generated by the application (`schema-generation.database.action` is `none`): create the `person`, `doctor` and `patient` tables before first run.

## Build and run

```bash
cd MediTrack_V7   && mvn clean package          # produces target/MediTrack.war
cd ../MediTrackClient && mvn clean package      # produces the client JAR
```

Deploy the WAR to WildFly (`mvn install` runs the plugin's `deploy` goal), then open `http://localhost:8080/MediTrack/faces/patients.xhtml`. The client expects the API at `http://localhost:8080/MediTrack/api`.

## Security

Threat model of the exercise: a single instance on a local machine, reached by trusted users. That assumption is doing a lot of work, and the limitations below follow from it.

What is in place:
- **No credential in the repository.** Database and SMTP credentials live in the server configuration; the code only resolves JNDI names.
- **Parameterised persistence.** Every query is JPQL through the `EntityManager`, with bound parameters where a value is involved; nothing is concatenated into a query string.
- **Server-side validation** of the quota before an assignment is recorded, on both the REST path and the queue consumer, counting patients in the database rather than trusting a loaded collection.
- **Bean Validation** on the required fields, and `@JsonbTransient` on the doctor's patient list so serialising a doctor does not expose every patient attached to them.
- **Personal data out of the logs.** Patient and doctor addresses are no longer written to the server log.

Known limitations, in order of severity:
- **No authentication or authorisation whatsoever.** Every REST endpoint and every Faces view is reachable anonymously, and the data model includes a free-text `details` field describing a patient's condition. Anyone who can reach the port can read, create and delete patient records. Adding container-managed security (Jakarta Security or Elytron with role constraints) is the first thing this application needs.
- **No transport security.** Everything is plain HTTP, including the client.
- **The e-mail address is the primary key** of `Person`. It therefore appears in REST paths, so in server logs and browser history, and a patient who changes address cannot simply be updated. A surrogate key with a unique constraint on the address would be the right model.
- **No rate limiting on the queue.** The REST endpoint accepts selection requests without limit and returns 202 immediately.
- **No audit trail.** `Person.timestamp` records creation only; assignments and deletions leave no trace.
- **No automated tests.** The logic worth covering is the quota check on both paths.
